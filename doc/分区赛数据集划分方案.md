# 分区赛数据集划分方案

## 目标

线下分区赛的目标不是单纯把数据集堆大，而是围绕评分项组织检测、识别和违法行为标记。

评分项可以拆成四条主线：

| 评分项 | 工程目标 | 主要模块 |
| --- | --- | --- |
| 车牌识别和标记 | 一张图中一个或多个车牌都能框出并识别 | YOLO + LPR |
| 角度、光照、延迟 | 透视矫正、增强训练、轻量部署 | 预处理 + YOLO/LPR 优化 |
| 特殊车牌识别 | 至少覆盖 3 种以上特殊车牌 | LPR 特殊牌训练 |
| 创新能力 | 行人识别，并标记一种或几种违法行为 | YOLO + 规则模块 |

因此推荐使用：

```text
YOLO 检测：plate / person / car / traffic_light
LPR 识别：蓝牌、绿牌、黄牌、特殊牌
道路理解：BDD100K drivable area 分割
违法标记：基于检测框、道路分割、红绿灯状态、视频跟踪和规则
```

## YOLO 类别方案

推荐最终 YOLO 类别为 4 类：

```text
0 plate
1 person
2 car
3 traffic_light
```

不建议把红灯、黄灯、绿灯拆成多个 YOLO 类别。原因是：

1. YOLO 类别越多，小目标类别越容易互相影响。
2. 交通灯本身已经是小目标，再拆颜色会增加检测难度。
3. BDD100K 原始 JSON 里有 `trafficLightColor`，颜色信息可以在转换时额外保存给后处理，不一定写进 YOLO 类别。
4. 比赛创新项只要求能完成一种或几种违法标记，不要求违法判断完全靠 YOLO 一个模型完成。

所以最稳的方式是：

```text
YOLO 负责检测 traffic_light 的位置
后处理负责判断红/黄/绿状态
规则模块负责判断是否违法
```

## 道路区域分割数据构成

为了避免每张图手动画 ROI，推荐额外训练一个轻量道路区域分割模型。它不属于 YOLO 检测数据集，而是单独的数据体系。

来源：

```text
D:\Tempcode\26IC\车牌数据集\中国车牌\BDD100K\bdd100k_drivable_maps
```

BDD100K 的 drivable map 通常包含三类区域：

```text
0 background
1 direct drivable
2 alternative drivable
```

工程上可以先合并成二分类：

```text
0 non_drivable
1 drivable
```

原因：

1. 违法规则只需要知道行人/车辆是否进入机动车可行驶区域。
2. 二分类分割模型更轻，部署更快。
3. 先把 direct 和 alternative 合并，后续需要更细时再恢复三分类。

推荐输出目录：

```text
datasets/drivable/
├── images/
│   ├── train/
│   ├── val/
│   └── test/
├── masks/
│   ├── train/
│   ├── val/
│   └── test/
└── drivable.yaml
```

推荐划分：

```text
沿用 BDD100K 图片级划分，或按 8:1:1 重新划分。
```

为了和 YOLO 检测保持一致，最终更推荐也按 8:1:1：

| 数据 | train | val | test | 合计 |
| --- | ---: | ---: | ---: | ---: |
| `BDD100K drivable` | 80000 | 10000 | 10000 | 100000 |

如果 drivable map 中存在额外 160k PNG，需要转换前按图片名和 BDD100K 100k 图片做匹配，只使用能与图片对应的 mask。

## 推荐划分方法

推荐使用“按来源分层的 8:1:1 图片级划分”。

也就是：

```text
不是把所有数据完全混在一起随机切。
而是每个数据集内部先按 8:1:1 划分，再合并各来源的 train/val/test。
```

这样做的好处：

1. 训练集数量充足，不浪费 CCPD2019 原本偏大的 test/val。
2. 每个来源在 train、val、test 中都有分布。
3. 多车牌图片按整张图划分，不会把一张图里的多个框拆到不同 split。
4. 使用固定随机种子，后续可复现。

推荐图片数量：

| 数据集 | train | val | test | 合计 |
| --- | ---: | ---: | ---: | ---: |
| `CCPD2019` | 273582 | 34198 | 34198 | 341978 |
| `CCPD2020` | 9420 | 1178 | 1178 | 11776 |
| `CRPD_multi` | 1268 | 158 | 159 | 1585 |
| `CRPD_double` | 4882 | 610 | 610 | 6102 |
| `CLPD` | 960 | 120 | 120 | 1200 |
| `BDD100K` | 80000 | 10000 | 10000 | 100000 |
| 合计 | 370112 | 46264 | 46265 | 462641 |

按来源汇总：

## 各数据集转 YOLO 方法

### CCPD2019 / CCPD2020

文件名中有 bbox：

```text
...-x1&y1_x2&y2-四角点-车牌编码-...
```

转为 YOLO：

```text
0 x_center y_center width height
```

### CRPD_multi / CRPD_double

标签格式示例：

```text
x1 y1 x2 y2 x3 y3 x4 y4 type plate_text
```

一行代表一个车牌。转 YOLO 时使用四角点外接矩形：

```text
xmin = min(x1, x2, x3, x4)
ymin = min(y1, y2, y3, y4)
xmax = max(x1, x2, x3, x4)
ymax = max(y1, y2, y3, y4)
```

类别固定为：

```text
0 plate
```

一张图片有多个车牌时，YOLO label 文件写多行。

### CLPD

`CLPD.csv` 格式：

```text
path,x1,y1,x2,y2,x3,y3,x4,y4,label
```

同样用四角点外接矩形转成 YOLO，类别固定为：

```text
0 plate
```

### BDD100K

BDD100K 用于行人、车辆和交通灯：

```text
person        -> 1
car           -> 2
traffic light -> 3
```

转换 YOLO label 时只写框：

```text
class_id x_center y_center width height
```

同时额外保存交通灯颜色元数据：

```text
meta/bdd_traffic_light_color.csv
```

建议字段：

```text
split,image_name,object_id,x1,y1,x2,y2,color
```

其中 `color` 来自 BDD JSON：

```text
attributes.trafficLightColor
```

## LPR 数据构成

YOLO 只负责检测目标位置：

```text
plate/person/car/traffic_light
```

LPR 负责识别车牌文字和特殊类型。建议目录：

```text
datasets/lpr/
├── blue_7/
├── green_8/
├── yellow/
└── special/
```

LPR 来源：

| LPR 分组 | 来源 |
| --- | --- |
| `blue_7` | CCPD2019、CLPD 普通 7 位、CBLPRD 普通蓝牌 |
| `green_8` | CCPD2020、CBLPRD 新能源小型/大型/拖拉机绿牌 |
| `yellow` | CBLPRD 单层黄牌、双层黄牌，CRPD/CLPD 中可识别出的黄牌 |
| `special` | CBLPRD 黑牌、警牌、使领馆、港澳、挂、学、临等特殊牌 |

从有四角点的数据生成 LPR 时，优先用四角点做透视矫正；从 CBLPRD 生成 LPR 时，直接使用其车牌图。

## 特殊车牌策略

特殊车牌得分主要靠 LPR，不靠 YOLO 细分类。

YOLO 阶段：

```text
所有车牌统一检测为 0 plate
```

LPR 阶段：

```text
根据颜色、位数、字符规则、模型输出判断特殊车牌类型
```

`CBLPRD-330k_v1` 有大量特殊牌，但缺少真实场景 bbox，所以不直接进入 YOLO。它应该重点进入 LPR，用来覆盖：

```text
黄牌、绿牌、警牌、学牌、挂车、港澳、使领馆、临牌等
```

如果后续测试发现特殊车牌“框不出来”，才需要额外补真实场景特殊车牌 bbox 给 YOLO。

如果是“框出来但识别错”，优先补 LPR 数据和规则。

## 违法行为标记方案

创新项不建议完全依赖 YOLO 类别完成，也不建议依赖每张图片手动画 ROI。推荐工程化链路：

```text
YOLO 检测 + 道路区域分割 + 交通灯颜色判断 + 视频跟踪 + 规则模块
```

各模块分工：

| 模块 | 输入 | 输出 | 作用 |
| --- | --- | --- | --- |
| YOLO 检测 | 原图/视频帧 | `plate/person/car/traffic_light` 框 | 找到目标位置。 |
| Drivable 分割 | 原图/视频帧 | 可行驶区域 mask | 判断人/车是否在道路区域。 |
| 交通灯颜色判断 | `traffic_light` 框 | red/yellow/green/unknown | 支撑闯红灯判断。 |
| 跟踪模块 | 连续帧检测框 | person/car track id 和轨迹 | 支撑横穿马路、车辆逆行判断。 |
| 规则模块 | 检测、分割、颜色、轨迹 | 违法标签 | 输出最终标记。 |

### 行人识别

需要：

```text
person 检测框
```

实现方式：

```text
检测到 person 后，在画面中标记行人框和类别。
```

这是最稳的创新项基础能力。

### 行人横穿马路

需要：

```text
person 检测框 + drivable area mask + 连续帧轨迹
```

实现方式：

1. YOLO 检测 `person`。
2. 取 person 框的底部中心点，近似作为脚点。
3. 如果脚点落在 `drivable` 区域内，说明行人进入机动车可行驶区域。
4. 连续几帧跟踪该 person，如果轨迹横向穿过道路区域，就标记为“行人横穿马路”。

这个方案不需要每张图手动画 ROI，比单纯 ROI 更适合泛化。注意它标记的是工程近似意义上的“行人进入/横穿机动车道”，比严格交通法规判断更容易落地。

### 行人闯红灯

需要：

```text
person 检测框 + traffic_light 检测框 + 红灯状态 + drivable area mask + 连续帧轨迹
```

实现方式：

1. YOLO 检测 `traffic_light`。
2. 对 `traffic_light` 框做颜色判断，得到 `red/yellow/green/unknown`。
3. YOLO 检测 `person`。
4. Drivable 分割判断 person 脚点是否进入可行驶区域。
5. 当红灯状态下，person 进入可行驶区域并产生横穿轨迹，就标记为“疑似行人闯红灯”。

注意：

- YOLO label 中不保存红绿灯颜色。
- 颜色可以用 BDD 的 `trafficLightColor` 做训练/验证，也可以部署时用 HSV 规则判断。
- 真正严格的闯红灯还需要知道“哪个交通灯控制哪条过街方向”，这个很复杂。比赛工程版可以先标记为“疑似行人闯红灯”。
- 如果现场交通灯很小或很糊，颜色判断要设置 `unknown` 状态，避免误报。

### 车辆逆行

需要：

```text
car 检测框 + drivable area mask + 视频连续帧跟踪 + 主车流方向估计
```

实现方式：

1. 用 YOLO 检测 `car`。
2. 用简单 IOU/ByteTrack/SORT 跟踪车辆 ID。
3. 只统计落在 `drivable` 区域内的车辆轨迹。
4. 从一段视频中估计主车流方向，或者根据场景初始化时自动统计多数车辆方向。
5. 如果某辆车轨迹方向与主车流方向明显相反，标记为“疑似车辆逆行”。

注意：

- 车辆逆行不能靠单张图片判断。
- 车辆逆行强依赖视频连续帧和稳定跟踪。
- 如果比赛主要是图片输入，优先展示“行人横穿马路”或“行人闯红灯”。
- 如果比赛允许视频演示，再做车辆逆行更合理。

## 推荐训练和部署路线

### 检测模型

训练一个统一 YOLO 模型：

```text
0 plate
1 person
2 car
3 traffic_light
```

优势：

1. 车牌、行人、车辆、交通灯一次检测完成。
2. 类别只有 4 个，不会像红黄绿交通灯细分类那样增加太多分类压力。
3. `traffic_light` 支持行人闯红灯规则。
4. 不在 YOLO 阶段细分蓝牌、绿牌、黄牌、特殊牌，保证车牌检测稳定。

### 视频数据的作用

视频数据建议找，但它主要不是用来训练 YOLO，而是用来验证和调试违法行为模块。

| 模块 | 是否需要视频 | 说明 |
| --- | --- | --- |
| YOLO 检测 | 不强制 | `plate/person/car/traffic_light` 用图片训练即可。 |
| LPR 识别 | 不强制 | 车牌识别主要用车牌图片和裁剪图训练。 |
| Drivable 分割 | 不强制 | BDD100K 图片和 mask 就能训练分割模型。 |
| 行人横穿马路 | 建议需要 | 连续帧能判断行人轨迹是否横穿道路。 |
| 行人闯红灯 | 建议需要 | 连续帧能判断红灯期间行人是否进入道路区域。 |
| 车辆逆行 | 强烈需要 | 逆行必须依赖车辆轨迹方向，单张图很难判断。 |

推荐寻找的视频类型：

```text
1. 固定摄像头路口监控视频
2. 有红绿灯、行人、车辆同时出现的视频
3. 有斑马线或明显道路区域的视频
4. 车辆主行驶方向明显的视频
5. 白天、夜晚、阴影、强光等不同光照视频
6. 如果能找到，额外收集车辆逆行或行人闯红灯样例视频
```

推荐格式：

```text
mp4 / avi
720p 或 1080p
15-30 fps
10 秒到 2 分钟
固定视角优先
```

视频数据在工程中的用途：

```text
1. 测试 YOLO + LPR + drivable 分割的完整流水线
2. 调试 person/car 跟踪
3. 调试行人横穿马路、闯红灯、车辆逆行规则
4. 做比赛现场演示素材
5. 统计系统端到端延迟
```

结论：

```text
图片数据负责训练检测、识别、分割模型。
视频数据负责验证行为判断、跟踪规则和系统演示。
```

### 当前 WTS_DATASET_TEST 的用法

本地路径：

```text
D:\Tempcode\26IC\车牌数据集\中国车牌\WTS_DATASET_TEST
```

这批 WTS 数据已经足够作为分区赛创新项的视频验证/演示素材，但它不是 YOLO 训练数据的主来源。

更准确的分工是：

| 数据类型 | 是否用于训练 | 主要作用 |
| --- | --- | --- |
| CCPD/CRPD/CLPD/BDD100K 图片和标注 | 是 | 训练 YOLO 四类检测。 |
| CCPD/CBLPRD/裁剪车牌图 | 是 | 训练 LPR 车牌识别。 |
| BDD100K drivable maps | 是 | 训练道路/可行驶区域分割。 |
| WTS_DATASET_TEST 视频 | 否，第一版不进训练 | 验证跟踪、违法规则和端到端演示。 |

当前检查到 `WTS_DATASET_TEST` 中有：

| 视频来源 | 数量 | 结论 |
| --- | ---: | --- |
| WTS 自有 `overhead_view` 事件视频 | 176 | 最推荐，用于违法行为判断。 |
| WTS 自有 `normal_trimmed/overhead_view` 正常视频 | 35 | 用于正常交通对照，检查误报。 |
| WTS 自有 `vehicle_view` 视频 | 78 | 可辅助展示，但多数不是主规则视角。 |
| `external/BDD_PC_5K` 视频 | 375 | 可用于通用检测/跟踪测试。 |

推荐优先使用：

```text
WTS_DATASET_PUBLIC_TEST/videos/test/public/*/overhead_view/
WTS_DATASET_PUBLIC_TEST/videos/test/public/normal_trimmed/*/overhead_view/
```

原因：

1. 固定路口/俯视视角，适合观察行人和车辆轨迹。
2. 大多为 1080p、约 30fps、几十秒到一分多钟，满足工程测试需要。
3. 附带 caption `event_phase`，并且有 `bbox_annotated` / `bbox_generated` 标注，可辅助验证行人/车辆框和行为阶段。

第一版落地顺序建议：

```text
1. 用图片数据训练/接入 YOLO 四类检测。
2. 用图片和 mask 训练/接入 drivable 分割。
3. 在 WTS overhead_view 视频上跑 YOLO + drivable。
4. 加 person/car 跟踪。
5. 先实现“疑似行人横穿马路/进入机动车道”。
6. 再加 traffic_light 颜色判断，实现“疑似行人闯红灯”。
7. 最后视时间实现“疑似车辆逆行”。
```

不要做的事：

1. 不要把 WTS public test 视频直接混入 YOLO 训练集。
2. 不要把 WTS 抽帧直接当训练图片，除非重新标注并确认不会造成评测数据泄漏。
3. 不要指望 WTS 替代 `BDD100K drivable_maps`，道路分割仍然需要单独训练或接入。

### 识别模型

训练 LPR 识别模型或多分支识别模型：

```text
blue_7
green_8
yellow
special
```

部署流程：

```text
原图/视频帧
  ↓
YOLO 检测 plate/person/car/traffic_light
  ↓
Drivable 分割得到道路/可行驶区域
  ↓
plate 框裁剪 + 透视矫正
  ↓
LPR 识别车牌字符和类型
  ↓
person/car/traffic_light + drivable mask + 跟踪结果进入违法规则模块
  ↓
输出车牌识别结果 + 违法行为标记
```

## 优先级

推荐按比赛得分优先级推进：

1. `plate` 检测和多车牌检测。
2. LPR 识别，重点补光照、角度、蓝绿黄和特殊车牌。
3. 加入 `person/car/traffic_light` 检测。
4. 训练或接入 drivable area 分割模型。
5. 先实现“行人横穿马路/进入机动车道”标记。
6. 再实现“疑似行人闯红灯”标记。
7. 如果有视频输入和时间，再实现“疑似车辆逆行”。

## 比赛要求覆盖情况

当前方案从数据和系统设计上已经覆盖分区赛要求，但最终得分还取决于训练效果、推理速度和现场测试表现。

逐项对照：

| 比赛要求 | 当前方案是否覆盖 | 对应模块 | 说明 |
| --- | --- | --- | --- |
| 对车牌进行识别并标记 | 覆盖 | YOLO `plate` + LPR | YOLO 负责标记车牌框，LPR 负责识别车牌号。 |
| 一个或多个车牌标记 | 覆盖 | YOLO `plate` | `CRPD_multi`、`CRPD_double` 专门补多车牌场景。 |
| 不同角度识别准确率 | 覆盖方向 | 透视矫正 + LPR | CCPD/CRPD/CLPD 提供角度变化，LPR 裁剪时优先用四角点透视矫正。 |
| 不同光线强度识别准确率 | 覆盖方向 | 数据增强 + LPR | CCPD 含亮度变化，训练时还需要增加亮度、对比度、模糊增强。 |
| 识别延迟低 | 方案考虑 | 轻量 YOLO + 轻量分割 + ONNX/量化 | YOLO 控制为 4 类，drivable 分割用二分类轻量模型，后续再做 ONNX/FPGA/量化部署。 |
| 特殊车牌识别 | 覆盖方向 | LPR special | `CBLPRD-330k_v1` 重点进入 LPR，覆盖黄牌、警牌、学牌、挂车、港澳、使领馆、临牌等。 |
| 大于三种特殊车牌 | 数据上可覆盖 | LPR 分组 + 规则 | 数据源具备多种特殊牌，后续需要在 LPR 训练和评测中单独统计每类效果。 |
| 行人识别 | 覆盖 | YOLO `person` | BDD100K 提供 person 检测数据。 |
| 行人横穿马路 | 覆盖工程方案 | `person` + drivable 分割 + 跟踪 | 标记“疑似行人横穿马路/进入机动车道”。 |
| 行人闯红灯 | 覆盖工程方案 | `person` + `traffic_light` + 颜色判断 + drivable 分割 + 跟踪 | 标记“疑似行人闯红灯”。 |
| 车辆逆行 | 覆盖工程方案，难度较高 | `car` + drivable 分割 + 视频跟踪 + 主车流方向 | 需要视频连续帧，单张图片无法稳定判断。 |

结论：

```text
数据集规划和系统路线已经对齐比赛要求。
下一步重点是把 YOLO、drivable 分割、LPR 三套数据真正转换出来，然后训练和验证。
```

建议验收指标：

| 模块 | 最低验收目标 |
| --- | --- |
| YOLO 检测 | 能稳定检测 `plate/person/car/traffic_light`，重点看 `plate` 和多车牌召回率。 |
| LPR 识别 | 蓝牌、绿牌、黄牌、特殊牌分别统计准确率。 |
| Drivable 分割 | 能区分道路可行驶区域和背景区域。 |
| 违法标记 | 至少稳定展示一种创新项，优先“行人横穿马路/进入机动车道”。 |

## 注意事项

1. YOLO 类别不要继续膨胀，当前推荐最多 4 类。
2. 交通灯颜色不要作为 YOLO 类别，保留给后处理或小分类器。
3. `CBLPRD-330k_v1` 不能替代 YOLO 检测数据，因为它缺少真实场景 bbox。
4. 多车牌图片不能拆散 split，同一张原图的所有检测框和 LPR 裁剪图必须属于同一个 split。
5. 训练检测模型时重点观察 `plate` 的 mAP，不能只看总体 mAP。
6. BDD100K 的 `car` 和 `traffic_light` 框数量很多，如果影响 `plate`，后续可以对 BDD 做采样。
7. Drivable 分割不进 YOLO 类别，应该单独训练轻量分割模型。
8. 违法行为建议输出“疑似”标记，避免规则近似导致过度承诺。
